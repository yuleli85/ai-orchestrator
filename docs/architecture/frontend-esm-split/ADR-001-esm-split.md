# ADR-001: 采用原生 ES 模块拆分前端

## 状态

已接受

## 背景

app.js 超过 1000 行，六类职责（工具、API、状态、渲染、SSE、路由）线性堆叠。同时 dev.js / arch.js 依赖 app.js 的全局函数，加载顺序即依赖顺序。`package.json` 声明 `"type": "module"`，Node 侧已经是 ESM；前端目前是无构建的普通 script，且 app.js 首行注释写明"一个 HTML 文件能被直接打开是这类工具的底线"。

需要决定：用什么方式拆分，以及是否接受拆分带来的运行方式变化。

## 备选方案

### 方案 A：原生 ES 模块拆分（无构建）

index.html 改为 `<script type="module" src="/src/main.js">`，按职责拆成 `src/shared/*`、`src/views/*`、`src/router.js`，用 import/export 显式声明依赖。

- 代价：无法从 `file://` 双击打开 index.html；需要重组全局 state 的传递方式（改模块单例）；迁移时需保留 SSE 和 DOM 更新行为，有回归风险。

### 方案 B：引入 Vite / esbuild 构建

加一个前端构建步骤，产出打包后的静态资源。

- 代价：引入 package.json 依赖和构建配置，`npm start` 之外多一条构建命令；对当前"无依赖、无构建"的运维形态是结构性改变；打包产物让浏览器里调试更难定位源文件。

### 方案 C：继续单文件，只用注释分区

不拆文件，在 app.js 内用注释分区维持现状。

- 代价：不解决任何耦合问题，文件继续膨胀；团队 review 时仍需在千行文件里跳转；等于不决策。

## 决策

选方案 A：原生 ES 模块拆分，无构建。

理由：

1. 本项目前端规模是"三个视图 + 一层共享工具 + 一张路由表"，不需要构建工具做 tree-shaking、polyfill、产物压缩；ESM 的静态 import/export 恰好解决"全局函数隐式依赖"这个核心痛点。
2. 后端已经是 ESM（`"type": "module"`），前后端心智一致。
3. `file://` 的损失是虚的：`api()` 用相对路径 `fetch('/api/...')`，双击打开时根本没有 `/api` 资源，前端任何操作都会失败。"直接打开可用"这条底线在引入客户端-服务端架构时已经失效，ESM 只是把失败从"第一次 API 调用"提前到"HTML 加载"。

## 后果

- 好处：依赖显式化，改 shared 函数签名会在开发期报 import 错误而非运行时炸；每个模块能用几十行～一两百行的规模 review；路由集中后 hash 逻辑只有一处。
- 代价：必须通过 HTTP 服务访问（`npm start` 起 server.js 即可，不新增命令）；三个视图文件必须一起迁（见 ADR-002）；迁移本身是纯前端文件重组，无后端改动，但 SSE 与 DOM 更新行为需要逐条回归。
- 后续约束：任何新前端代码必须走 ESM import，禁止再往 window 上挂全局函数；`src/` 下不再允许出现"定义全局变量供其他文件使用"的写法。
