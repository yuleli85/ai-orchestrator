# 总控台 · AI Orchestrator

一句话丢进去，它自己判断该拆成几块、每块交给哪个角色、哪些能同时开工，然后真的并行跑完，最后合并成一份能直接用的成果。

不是"任务清单生成器"——子任务是真的调模型执行，产出是真的文档。

里面有两个智能体：

- **总控台**：拆任务、派活、并行执行、合并交付。子任务产出方案与文档。
- **开发智能体**：直接在你的项目目录里读代码、写代码、跑构建和测试，改完自己验证，全程可回滚。

```
你说：帮我策划一个 15 秒的投资类短视频，讲 Python 全栈技术路线图
     ↓
总控拆解：4 个任务 / 3 个角色 / 2 波并行
     ↓
并行执行：产品经理定策略 ┐
         架构师核事实 ┘ 同时跑 → 写手写脚本 ┐
                                    设计师出分镜 ┘ 同时跑 → 评审官挑毛病
     ↓
合并交付：一份 6800 字的开拍定稿
```

开发智能体是另一条路径——它不动嘴，动手：

```
你说：给 slugify 加 maxLength 和 separator 参数，补测试
     ↓
读代码：list_files → read_file src/strings.js → read_file test/run.js
     ↓
出方案：改哪 2 个文件、怎么改、跑什么命令验证   ← 你确认这一屏
     ↓
动手：edit_file → run_command `node test/run.js` → 看到失败 → 改 → 再跑
     ↓
交付：改了 2 个文件、3 条命令、测试 15 例全过；不满意一键回滚
```

## 怎么用

**第一步：说人话。**
输入框里写你要解决的事，不用想怎么分工。写"给对账模块做技术方案，要能给开发直接用"，不要写"请帮我拆解成 5 个任务"。

**第二步：看它怎么拆。**
出来的是分派方案：总控的理解、它替你做的假设、每个子任务由谁负责、要交什么、怎么算合格、谁依赖谁。
两处不满意可以直接改：

- 点任务卡片上的角色徽标 → 换个人做
- 点「重新规划」→ 让它重拆一遍

**第三步：点执行。**
每张卡片会实时长出内容，跑完自动合并成「交付成果」，可导出 Markdown。

`Ctrl / Cmd + Enter` 直接提交。

## 开发智能体

顶栏切到「开发」标签，这是另一套东西：它不是在写文档，它是在改你的代码。

### 三步走

1. **选工作区**：点「更换目录」，选一个项目目录。它只能在这个目录内读写文件、执行命令。
2. **说清楚要改什么** → 点「出实施方案」（约 10~25 秒）。
   它会真的去读你的目录结构和关键文件，然后给出：要改哪些文件、每处改什么、按什么顺序、跑什么命令验证、可能踩什么坑。
3. **看一眼，没问题点「确认，开始执行」。** 卡片上会实时刻出：读了哪个文件、写了哪个文件、跑了什么命令、退出码多少。

不满意方案就点「重新出方案」重来，不会动你的文件。

### 它手上有什么

| 工具 | 用途 |
|---|---|
| `list_files` | 看目录结构 |
| `read_file` | 读文件全文（改文件前必须先读） |
| `search` | 全项目正则搜索，返回 `文件:行号: 内容` |
| `write_file` | 写文件（新建或整体覆盖，覆盖前自动备份） |
| `edit_file` | 局部替换一段文本，改已有文件优先用这个 |
| `run_command` | 跑构建、测试、装依赖、看 git 状态 |
| `finish` | 声明完成，必须带上验证命令的真实输出 |

### 四条安全边界

这部分是整个功能能不能用的前提，都写成了可执行的测试（`scripts/sandbox.test.mjs`，41 条断言）：

1. **路径限制在工作区内**：绝对路径、`../`、指向区外的符号链接一律拒绝。
2. **命令走白名单**：`rm -rf`、`format`、`git push`、`git reset --hard`、`curl`/`wget`、`sudo`、杀进程等直接拒绝；命令里出现盘符绝对路径或 `../` 也拒绝。
3. **覆盖前自动备份**：原文件存到 `data/dev-runs/<runId>/backup/`，点「回滚这次改动」即可整体还原（新建的文件会被删掉）。
4. **迭代有上限**：最多 40 步、单条命令 5 分钟超时、总 token 预算超了强制收尾——不会无限重试烧钱。

### 总控也能派活给它

在总控的输入框旁边选好工作区后，规划引擎会把"要写代码"的子任务派给「开发工程师」，这时候子任务是真的在改文件，不是出方案。

实测一个 4 任务的例子：

```
T1 [开发工程师] 实现 src/date.js           ┐ 并行
T2 [测试工程师] 设计测试用例清单            ┘
T3 [开发工程师] 编写并跑通 test/date.js     ← 依赖 T1 T2
T4 [技术写手]   撰写模块接入说明            ← 依赖 T1
```

跑完 4/4 交付，`src/date.js` 和 `test/date.js` 真的落在磁盘上，`node test/date.js` 真的 14 例全过。

同一工作区在同一时刻只允许一个开发任务在跑（会互相覆盖），其它角色照常并行。

## 架构智能体

顶栏切到「架构」标签。和开发智能体的分工是干净的：**开发智能体改代码，架构智能体只出文档**——它一个字节的源码都不会动，写死的边界在工具层，不在提示词里。

### 为什么分两段，还刻意停住

架构设计的分水岭不在"写文档"，在"选哪条路"。所以中间必须停下等人：

1. **诊断（只读）**：扫全项目 → 出问题清单 → 给 2~3 个候选方案，每个都写清改什么、好处、代价、工作量、什么前提下才成立。
2. **你选方向** → 才开始写文档。

不选就不往下走。这一步省不得——同一句"app.js 该不该拆"，选"原生 ESM 拆分"和选"保持单文件只做分层"产出的文档是反的，先写再改等于白跑一轮。诊断态在状态机里是独立的一档 `DIAGNOSED`，不是中间过渡态。

### 诊断不是把代码丢给模型

先用 `lib/archprofiler.js` 在本地把项目画像算出来。纯 JS 计算，**0 token**，实测 42ms 扫完 49 个文件的 Java 工程、36ms 扫完 19 个文件的 JS 工程：

| 算什么 | 拿来干什么 |
|---|---|
| 源码根推断、语言分布、文件数 | 决定读哪些样本文件 |
| 模块聚合（按目录归一） | 判断模块边界到底清不清晰 |
| import 解析（JS/TS/Java/Kotlin/Python/Go） | 出模块依赖图 |
| 循环依赖检测（DFS 找环 + 归一化去重） | 问题的硬证据，不是模型猜的 |
| 五层识别 + 分层违规（presentation/application/domain/infrastructure/shared + 允许依赖表） | 例：domain 反向依赖 infrastructure |
| 上帝模块（单文件出度占比） | 例：`BizException` 被 10 处引用 |
| 耦合热点（被依赖次数 top） | 改动的爆炸半径有多大 |

画像最后渲染成一段文本喂给模型。所以它看到的是「你项目里有 3 个环、2 处分层违规、1 个出度 67% 的上帝模块」，不是「请分析这个项目」。这两个输入的输出质量差一个量级。

扫描器有三个容易踩的坑，都修了：测试代码不计入依赖图（否则 `src/test` 会凭空造出虚假耦合）；备份目录、`data/dev-runs`、`node_modules` 一律跳过（否则会扫到自己上次的备份）；平铺的容器目录不会被误判成源根（否则 `lib/` 下 12 个文件全落进 `(root)`，`lib` 被误报成上帝模块）。

### 写文档阶段它手上有什么

| 工具 | 用途 |
|---|---|
| `list_files` | 看目录结构（已过滤 `data/`、`node_modules` 等噪声） |
| `read_file` | 读文件，首读 16KB；**同一个文件重读只回显开头 4KB** |
| `search` | 正则搜 `文件:行号: 内容`，定位实现细节首选 |
| `deps_of` | 查某个文件的上下游依赖，画像只算一次，之后复用 |
| `write_doc` | 写 `docs/` 下的 `.md` |
| `finish` | 声明收工，必须已写出文档 |

产出一般是这几份（按项目复杂度增减）：`README.md`（文档索引）、`architecture.md`（目标架构 + 模块职责 + 数据流，Mermaid 图画在 markdown 代码块里）、`ADR-00N-*.md`（每个关键决策一份）、`contracts.md`（模块间接口契约）、`roadmap.md`（分几步走）。

### 六条边界
前两条是架构智能体特有的，后两条和开发智能体共用同一套机制：

1. **只读源码，只写文档**：`write_doc` 的路径校验在工具层强制——必须是 `docs/` 下、必须是 `.md`、不能含 `..`。传 `server.js` 会被直接拒。
2. **不许覆盖别的运行**：同一工作区做多轮设计时，`docs/` 下会有历史产出。写之前会先列出已有文件塞给模型，要求 ADR 编号接着最大号往后排、文件名带本次主题；真撞上别人的同名文件会被拒，除非显式传 `overwrite: true`。这条是补上去的——先前的版本让第二轮从 `ADR-001` 重新编号，把上一轮的 `README.md` 整份覆盖了，目录里两套结论互相矛盾。
3. **不许交白卷**：模型想调 `finish` 但一份文档都没写，工具层拒绝并回喂「[拒绝] 你的交付物是 `docs/` 下的 Markdown 文件，不是聊天正文」。连续拒 3 次直接中止，不陪着耗预算。
4. **覆盖前备份、可回滚**：改到的文件存到 `data/arch-runs/<runId>/backup/`（镜像工作区相对路径），点回滚时新建的删掉、改过的还原。
5. **迭代有上限**：`ORCH_ARCH_MAX_STEPS`（默认 24 步）、读文件超过 12 个直接叫停、总 token 预算过半还没动笔就强制催写、超预算强制收尾。这三道闸是实测加的——第一版跑出过「用了 7 步 / 219745 token，一份文档没写」。
6. **进程被杀不会留下僵尸任务**：重启时把 `CREATED/SCANNING/DESIGNING` 一律收尾成 `INTERRUPTED`，已写到磁盘的文档保留。否则列表里那条永远显示"进行中"，点进去也没反应。

### 实测

拿本工程自己开刀，题目是真问题：「前端 app.js 已经一千多行，所有视图逻辑混在一个文件里，判断该不该按视图拆分，以及怎么拆才不影响现在的 hash 路由」。

诊断用了 160 秒（扫 19 个 JS 文件 + 读 14 个样本 + 一次模型调用），出来 5 个问题、3 个方案，推荐方案 A。选 A 后写出 **7 份文档 433 行**：

```
README.md                              34 行   文档索引
architecture.md                       157 行   目标架构 + 模块依赖图
ADR-001-http-routers-by-domain.md      41 行   决策：HTTP 路由按域拆
ADR-002-sse-handler-factory.md         46 行   决策：SSE handler 工厂化
ADR-003-tomarkdown-location.md         38 行   决策：toMarkdown 归属
contracts.md                           82 行   模块间接口契约
roadmap.md                             35 行   分四步走
```

质量抽查：ADR-002 把三个 SSE handler 的 8 个差异点参数化成一张表；每份 ADR 的 `## 后果` 都写了「好处 / 代价 / 后续约束」三段；风险第一条直接命中本工程历史上的真实踩坑「前端先连 SSE 再 POST 启动，导致事件全丢」。

越权验证：`GET /api/arch/runs/:id/doc?path=server.js` 返回「这份文档不属于本次运行」。

### 也能从总控派活

总控的规划引擎遇到"要定架构"的子任务会派给「架构师」角色，带工作区时走的是同一套诊断流程（`role.scan === true`），结果转成 Markdown 表格汇总进总控报告。差别是总控里不等人选方案，直接用诊断给出的推荐项——批量场景下没法逐个人工确认。

## 几个关键设计

**为什么规划用快模型、汇总也用快模型？**
实测同一任务：快模型 27 秒拆 4 个任务、角色分配合理；强模型 55 秒拆 4 个任务，质量没有可感知差异。汇总同理（184 秒 → 42 秒）。强模型留给真正需要的角色（架构师、数据分析师）。这是一次实测后的取舍，不是拍脑袋。

**为什么要"先看方案再执行"？**
拆错了直接跑，烧的是钱和时间，还得重来。看一眼分派表只要 5 秒，能挡掉大部分跑偏。

**为什么按依赖分层执行？**
层内并发、层间串行。没有依赖的任务必须同时跑，否则这个工具和"一个个问 AI"没区别。所以 prompt 里对 `dependsOn` 的要求很硬：**B 没有 A 的产出就做不下去**才算依赖，"可以参考"不算。

**为什么禁止拆出"汇总文档"任务？**
系统本身有汇总环节。让模型再派一个写手去合并，等于同一件事做两遍。

**token 预算给得很大（16000）**
推理模型会先思考再说话，预算给小了会出现 `content` 为空、`finish_reason=length`。第一次重试会把预算翻倍——原样重跑只会再失败一次。

**开发智能体为什么拆成"方案 → 确认 → 执行"两段？**
跳过方案直接写代码，一旦方向错了就是一堆白改的文件和一堆要回滚的备份。方案阶段只读不写（`list_files` / `read_file` / `search`），10~25 秒，能挡掉绝大多数理解偏差。

**工具报错为什么不抛异常，而是回喂给模型？**
这是"会干活"和"一遇错就整轮失败"的分界线。模型看到"在 a.js 里找不到要替换的内容"，才会自己去 `read_file` 确认原文再改；抛异常只会让它整段重来，而重来往往犯同样的错。

**为什么同一工作区只允许一个开发任务在跑？**
两个智能体同时改一个目录必然互相覆盖，而且报错信息会互相污染（A 改到一半 B 跑了测试）。所以按工作区加锁串行，其它角色照常并行——锁只锁真正要写盘的那一个。

| POST | `/api/arch/runs/:id/cancel` | 中止 |
| POST | `/api/arch/runs/:id/rollback` | 回滚本次产出的文档 |
| GET | `/api/arch/runs/:id/doc?path=` | 读本次产出的某份文档（只允许本次运行写过的路径） |
| GET | `/api/arch/runs/:id/events` | SSE 事件流 |
| DELETE | `/api/arch/runs/:id` | 删除记录 |

架构 SSE 事件：`arch:snapshot` / `arch:status` / `arch:scan:start` / `arch:scan:done` / `arch:analyzing` / `arch:diagnose:done` / `arch:step` / `arch:assistant` / `arch:tool` / `arch:tool:result` / `arch:doc` / `arch:warning` / `arch:done` / `arch:error`。

`arch:warning` 是给「模型想收工但没写文档」这类被拦截的动作用的——它不该只出现在服务端日志里，用户得看得见。

总控 SSE 事件：`job:snapshot` / `job:start` / `layer:start` / `task:start` / `task:delta` / `task:done` / `task:error` / `task:retry` / `summary:start` / `summary:delta` / `summary:done` / `job:done`。

连接建立时先推一份 `job:snapshot`（含各任务当前状态与已有产出），因为客户端是"先 POST execute 再订阅"，中间几百毫秒可能已经漏掉事件。

## 自测

```bash
node scripts/e2e.mjs                                    # 用内置示例任务
node scripts/e2e.mjs "你的任务描述"                      # 用自己的任务
```

会真实调用模型跑完整流程，打印：规划耗时、分工结构、每波并发情况、每个任务耗时、并行是否真的发生（用服务端记录的时间算重叠，不依赖事件）、导出预览。

```bash
node scripts/sandbox.test.mjs                           # 沙箱安全边界，41 条断言，秒级，不烧 token
node scripts/devtest.mjs "任务" 工作区路径               # 开发智能体进程内直跑（不经 HTTP）
node scripts/devhttp.mjs 工作区路径 "任务"               # 开发智能体全链路（建任务→方案→执行→校验落盘）
node scripts/archprofiler.test.mjs                      # 项目画像扫描器，19 条断言，秒级，纯本地
node scripts/archguard.test.mjs                         # 架构智能体写入边界 + 回滚，11 条断言，秒级
node scripts/archhttp.mjs 工作区路径 "题目"              # 架构智能体全链路（诊断 → 选方案 → 写文档）
```

`archprofiler.test.mjs` 在临时目录里现造一个假的烂项目（3 个环、2 处分层违规、1 个上帝模块、一堆测试文件），验证画像能全抓出来、且**不把测试代码算进依赖图**。这类断言比"跑通不报错"有用得多。

`archhttp.mjs` 默认只跑诊断阶段（省 token），加 `--full` 才跑写文档阶段。

`devhttp` 最后做的是**硬校验**：不只看模型说自己完成了，而是检查状态是否为 `DONE`、有没有真实文件改动、有没有成功的验证命令。

`node scripts/devhttp.mjs "C://path//to//proj" "新建 src/x.js 实现 f()，写测试并跑通"`

## 已知限制

1. **单进程内存态**：执行中的任务靠进程内 EventEmitter 推事件，服务重启会丢失正在跑的任务（已完成的结果都在 `data/state.json` 里）。
2. **无鉴权**：默认只监听 `127.0.0.1`。要给别人用得先加登录，并改成 `HOST=0.0.0.0`。
3. **总控的普通子任务不读文件、不联网**：除「开发工程师」以外的角色只能基于任务描述和上游产出工作。要读仓库就派给开发工程师。
4. **并发数固定**：`ORCH_CONCURRENCY` 全局生效，不能按任务单独设。
5. **状态只存在本地 JSON**：任务多了（>200）会滚动淘汰，不适合当长期归档用。
6. **开发智能体不写 git 提交**：它改文件、跑命令，但不会帮你 commit/push（推远端的命令是被禁止的）。改完自己 review 再提交。
7. **回滚只覆盖本次改过的文件**：如果它改文件之后你又手工改了同一个文件，回滚会把你手改的也冲掉。
8. **不擅长跨模块大改**：一次适合做一个内聚的改动。要重构一个模块，拆成几个任务分开跑比一次让它改 20 个文件靠谱。
9. **命令白名单是硬边界**：需要 `docker`、`kubectl`、`terraform` 这类命令时会被拒绝，得自己在 `lib/sandbox.js` 的 `ALLOW_CMDS` 里加。
10. **架构智能体只写文档，不动代码**：这是设计选择不是缺陷——但意味着"文档写完了"离"重构完成了"还有一段人工工作。它给的是可执行的迁移顺序，不是自动化重写。
11. **架构诊断的准确度取决于依赖解析**：目前支持 JS/TS、Java/Kotlin、Python、Go 的 import/use/require。C#、PHP、Ruby 的文件会被识别语言但解析不到依赖边，这类项目只能拿到模块规模和文件分布，拿不到环和分层违规。
12. **单次诊断有样本上限**：`ORCH_ARCH_SAMPLE` 默认只读 14 个文件。超大工程（几千文件）容易选出代表性不足的样本，建议先用它扫出问题清单，再针对某个子系统单独开一轮。
13. **架构文档不自动重算**：代码演进后文档会过期。要更新就再开一轮诊断，它不会做"增量比对上次结论"。
14. **多轮设计共用 `docs/architecture/`**：不会自动按主题分目录。防护只到"不许无声覆盖"这一层——编号是否连续、README 是否互相取代，靠模型自己按规则处理。本工程自己就踩过这个坑（两轮不同主题撞了 ADR 编号），现在按主题分了 `backend-http-split/` 和 `frontend-esm-split/` 两个子目录。要紧的项目建议一轮一个主题、一个主题一个子目录。
